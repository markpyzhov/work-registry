# Agent Instructions

Canonical instruction file for agents working in this registry. Keep it compact and
durable; task runbooks live in `automation/`. Copy into your registry root and adapt
the placeholders.

## File ownership

- `AGENTS.md` — durable rules: conventions, routing, agent behavior.
- `CLAUDE.md` — compatibility pointer only; it references this file.
- `integrations/<source>.md` — registry data only: source IDs, URLs, destinations,
  sync and review anchors.
- `automation/*.md` — task workflows, schedules, stop conditions.
- `<project>/<source>/`, `general/<source>/` — synchronized evidence.
- `work-states/`, `briefs/` — generated by the agent; humans correct them on branches.
- `work-states/comments/` — durable `CMT-*` records created by work-state review;
  never edited by hand.

## Core rule

The integration files are the source registry and a strict allowlist. Before writing
any source-derived file, read the registry and use the destination listed there;
existing destinations are canonical even if a routing rule would now choose
differently. A bare URL is an unmapped placeholder: resolve metadata, assign a
`SRC-*` ID, and add a registry entry before treating the file as tracked.

IDs are stable and append-only: never renumber `SRC-*`, `WS-*`, `T###`, `S#`, or
`CMT-*`.

If instructions conflict: explicit user request → registry data → this file → task
workflow details.

## Paths

Run from the repository root. Use repo-relative paths everywhere; never introduce
absolute local paths.

## Source entry shape

```markdown
- `SRC-<SYSTEM>-<PROJECT>-<YYYY-MM-DD>-<TITLE-SLUG>` — [Source <title>](<url>) — [Destination](<relative/path.md>)
  - Last reviewed revision: not reviewed
```

Wrap the destination in angle brackets only when the path contains spaces.

## Review vs sync anchors

- `Last reviewed revision` — work-state review coverage only; never use it to decide
  whether to download.
- Sync state uses separate anchors: `Last source sync`, `Remote modified`,
  `last_checked`. Never move an anchor backward.

## Routing

- Project evidence → `<project>/<source>/`, for example `alpha/slack/`,
  `alpha/google-docs/`, `alpha/fireflies/`, or `alpha/clickup/`.
- Cross-project evidence → `general/<source>/`.
- An existing registered destination never moves automatically.
- Unclear project → `general/<source>/`, flagged in the summary.

## Automation tasks

Pipeline order: configured sync tasks in a fixed order → work-state review → brief.
Adapt the supplied Slack → Fireflies → Google Docs → ClickUp order to the
integrations in use.

## Commit policy

- The runner starts on an up-to-date `main`. Fetch, pull, push, and backup are runner
  responsibilities, not task steps.
- Synced sources and generated state commit to `main`; logic changes
  (`automation/`, `AGENTS.md`) use branch + review.
- Automation commits under a dedicated bot identity (one-shot `git -c`, never
  persisted) with `Automation: work-registry-bot` in the body.
- Never set bot `user.name` or `user.email` with `git config` or
  `git config --global`.
- Preflight with `git status --short`; stage only files the task touched; leave
  unrelated changes alone. If a file the task may write is already changed, skip it
  and report the conflict. A clean run commits nothing.

Every task uses this pattern, replacing the subject and file list:

```bash
git status --short
git add -- <files touched by this task>
git diff --cached --quiet && exit 0
git -c user.name=work-registry-bot \
    -c user.email=bot@work-registry.local \
    commit -m "<task>: <summary>" -m "Automation: work-registry-bot"
```
